# Fork releases (lauchiwa/edgeever)

This repository is a customized fork of upstream EdgeEver (`tianma-if/edgeever`).
It builds and publishes its own Windows, Linux and macOS desktop releases, plus a
signed Android APK, on its own Releases page, and installed fork clients update only from there. Upstream is never
written to. 中文：[fork-releases.zh-CN.md](fork-releases.zh-CN.md).

Scope today: **Windows x64 desktop, Linux x64 AppImage, macOS arm64 and x64
(see [macOS](#macos)), Android arm64 APK (see [Android](#android)), plus the
server image** `ghcr.io/lauchiwa/edgeever` (API and the browser Web app). iOS
fork builds are not published. Fork-only features such as
[encrypted notes](encrypted-notes.md) need both a fork client and a server
running the fork image.

## The version

```text
vX.Y.Z-rc.N
```

- `X.Y.Z` is the upstream release this fork is synced from, copied verbatim.
  `main` keeps that bare version in `package.json`; the suffix is applied only
  when a release is built (`fork-release-version.mjs apply`).
- `N` counts this fork's releases on that base, from `0`.

```text
synced upstream 1.119.0   v1.119.0-rc.0
fork change released      v1.119.0-rc.1
upstream ships 1.120.0    v1.120.0-rc.0
```

A bare `vX.Y.Z` is never published: SemVer ranks it above every `-rc.N`, so it
would pin installs to it for good. `rc` is a custom channel: electron-updater
offers an `rc` client only other `rc` releases, while `alpha`/`beta` would also
accept stable releases. Releases must only ever increase: the updater picks the
most recently published `rc` release, and `fork-release-version.mjs next`
refuses a base below one already released.

## Where the fork differs, and what guards it

| Area | Fork behaviour | Guard |
| --- | --- | --- |
| Identity | `apps/desktop/src/main/fork-config.mjs` (+ renderer mirror `packages/shared/src/fork-config.ts`) | `scripts/fork-invariants.test.mjs` |
| Updates | electron-builder publishes to and updates from this fork; channel files `rc.yml` (Windows), `rc-linux.yml` (Linux) and `rc-mac.yml` (macOS) | invariants, `windows-update-metadata.test.mjs`, `fork-linux-release.test.mjs`, `fork-macos-release.test.mjs` |
| Windows update trust | only this fork's Ed25519 keys, only `X.Y.Z-rc.N` | `windows-update-trust.test.mjs`, pinned fingerprints |
| Linux update trust | as upstream's Linux Preview: HTTPS from this fork's Releases, the sha512 in `rc-linux.yml` (checked by electron-updater) and an independent `SHA256SUMS-linux.txt`; **no signed manifest** | `fork-linux-release.test.mjs`, a real AppImage update before publishing |
| macOS update trust | apps signed with this fork's self-signed certificate; Squirrel.Mac installs an update only if it satisfies the running app's designated requirement (bundle id `org.edgeever.desktop` and the SHA-1 of either pinned certificate), after electron-updater checks the sha512 in `rc-mac.yml`; `SHA256SUMS-macos.txt` lists every zip and disk image. Not notarized | `fork-macos-release.test.mjs`, invariants, a real signed-app update on each architecture before publishing |
| Links | diagnostics, feedback, desktop and Android APK downloads point at the fork, and the Google Play entry is hidden until the fork has its own listing; server release notes point at the fork for a fork image (`vX.Y.Z-rc.N`) and upstream otherwise; deliberate upstream links remain (upstream server release notes, plugin docs, the mobile app's upstream update check and homepage link, poster fonts pinned to an upstream commit) | upstream-literal scan with an allowlist; download menu check |
| Android | same package `org.edgeever.mobile`, fork keystore; expo-updates, the in-app APK update and the Google Play in-app update are off, so upstream OTA updates never replace fork code and the app never offers upstream's APK; unlocks encrypted notes natively | invariants, `fork-workflows.test.mjs`, manifest check in the shared build action, signer check when signing and again before publishing |
| ACP | Windows ACP fixes | ACP tests, invariants |
| Encrypted notes | client-side encryption; the server refuses plaintext overwrites and advertises `features.encryptedNotes` | `encrypted-note*.test.mjs`, `tests/e2e/encrypted-note.spec.ts` |
| Server image | `fork-docker-image.yml` publishes rc tags only, never `latest` | `fork-workflows.test.mjs` |

The invariants test exists because an upstream merge can apply cleanly and
still undo the fork, for example by adding a new `tianma-if/edgeever` literal.

## Signing keys

- Two Ed25519 keys: **primary** signs releases; **backup** is kept cold and
  only signs a key-rotation release if the primary is lost or leaked. Both
  public keys are pinned in `fork-config.mjs`; their fingerprints are pinned in
  the invariants test.
- Private keys are passphrase-encrypted PKCS#8 files outside the repository,
  generated by `scripts/fork-generate-update-keys.mjs`.
- To release without manual steps, the **primary** key and its passphrase are
  secrets of the `fork-release` GitHub Environment. Only the release
  workflow's `publish` job can read them; it installs nothing and runs only
  the repository's dependency-free scripts. The trade-off: anyone who controls
  this GitHub account or a release run can ship an update installed clients
  accept. The **backup** key never enters GitHub, so a leaked primary can
  still be replaced by a key-rotation release signed locally with the backup.
- Set or replace the secrets yourself, in Windows Terminal (`cmd` redirection
  keeps the key out of the shell and the passphrase is typed hidden):

  ```powershell
  cmd /c "gh secret set FORK_WINDOWS_UPDATE_SIGNING_KEY --env fork-release -R lauchiwa/edgeever < %USERPROFILE%\.config\edgeever-fork\windows-update-ed25519-primary.pem"
  gh secret set FORK_WINDOWS_UPDATE_SIGNING_PASSPHRASE --env fork-release -R lauchiwa/edgeever
  ```
- Losing both private keys means installed clients can no longer auto-update;
  they must reinstall by hand. Keep backups in a password manager or on
  encrypted offline storage.

### macOS signing certificates

Without an Apple Developer ID, macOS releases are code-signed with two
self-signed certificates (RSA-3072, 20 years): the **primary** signs every
release; the **backup** stays cold for a rotation release. Every fork app
carries a designated requirement naming both, so a later app signed by either
installs over it; a third certificate needs a release signed by one of these
two first. Losing both private keys means installed Macs must reinstall by
hand.

One-time setup, by the maintainer (the agent never reads the keys or
passphrases). It can be done on a Mac or on Windows:

1. Create the Environment: Settings → Environments → New environment
   `fork-macos`, with the same deployment rules as `fork-release`. Set them
   before adding any secret.
2. From the repository (Node 24; the passphrases are typed hidden, use two new
   ones of at least 16 characters). On a Mac, in Terminal:

   ```sh
   node scripts/fork-generate-macos-signing-certificates.mjs
   ```

   On Windows, in PowerShell or Windows Terminal (Git Bash cannot hide input):

   ```powershell
   node scripts/fork-generate-macos-signing-certificates.mjs --skip-self-test
   ```

   On a Mac it signs a test binary with each identity in a throwaway keychain
   and checks the result before writing anything (`"selfTested": true`).
   Elsewhere that self-test is skipped (`"selfTested": false`): the
   `macos-sign` and `macos-verify` jobs still check the primary before any
   release is published, but the backup is not exercised until it signs a
   rotation release, so test it on a Mac when one is available. Signing a
   release locally also needs a Mac. Either way it writes the encrypted keys
   and `macos-signing-certificates.json` to `~/.config/edgeever-fork`
   (`%USERPROFILE%\.config\edgeever-fork` on Windows) and prints both
   certificates.
3. Pin both `certificatePem` values in `FORK_MACOS_SIGNING_CERTIFICATES` in
   `apps/desktop/src/main/fork-config.mjs` through a pull request. Until then
   the release gates refuse to build a release.
4. Store the primary key and its passphrase. On a Mac:

   ```sh
   gh secret set FORK_MACOS_SIGNING_KEY --env fork-macos -R lauchiwa/edgeever < ~/.config/edgeever-fork/macos-signing-rsa-primary.pem
   gh secret set FORK_MACOS_SIGNING_PASSPHRASE --env fork-macos -R lauchiwa/edgeever
   ```

   On Windows:

   ```powershell
   cmd /c "gh secret set FORK_MACOS_SIGNING_KEY --env fork-macos -R lauchiwa/edgeever < %USERPROFILE%\.config\edgeever-fork\macos-signing-rsa-primary.pem"
   gh secret set FORK_MACOS_SIGNING_PASSPHRASE --env fork-macos -R lauchiwa/edgeever
   ```

5. Move `macos-signing-rsa-backup.pem` to offline storage, and keep both
   passphrases in a password manager.

## Local checks

`fork-ci.yml` runs every gate from scratch on each pull request that can
affect them, and that run is what must pass (see
[Documentation-only changes in CI](#documentation-only-changes-in-ci)).
Locally, check only what a change can affect:

- Docs only: nothing.
- Fork scripts or workflows: the affected test files, for example
  `bun test scripts/fork-workflows.test.mjs`.
- Application code:

  ```sh
  node scripts/fork-check.mjs          # fork tests + both typechecks
  node scripts/fork-check.mjs --full   # also build:web
  ```

  The typechecks are the repository's own `bun run typecheck` and
  `bun run typecheck:mobile` with `--incremental`; TypeScript keeps its state
  in `node_modules/.cache/edgeever-fork`, so a later run rechecks only what
  changed. The first run takes as long as a full one. If the results ever look
  stale, delete that directory.

`fork-check.mjs` and the `checks` job of `fork-ci.yml` list the same fork
tests; `scripts/fork-check.test.mjs` fails if they drift apart.

### Documentation-only changes in CI

Each `fork-ci.yml` job first runs `scripts/fork-ci-scope.mjs`, which needs
only Node. It skips the job's remaining steps when every file changed against
`main` is Markdown under `docs/` or at the repository root that no code, test
or build reads. The jobs still report, so the required checks pass in about
half a minute. The same applies to the push of that merge to `main`.

Everything else runs every check: any other file (images, workflows,
scripts), a document listed in `READ_DOCS` (the READMEs, `AGENTS.md`, and the
deployment, plugin and import guides the site, app or tests read), a manual
run, and any case the script cannot classify. The workflow skips only on an
explicit `run=false`, so a failing scope step runs the checks.
`scripts/fork-ci-scope.test.mjs` fails when code reads a document missing from
`READ_DOCS`; add it there.

## Syncing an upstream release

Only formal upstream releases are followed, never upstream `main`.
`main` is protected (pull requests only, no force push or deletion), and
upstream's `sync-edgeever-upstream.yml` is disabled in this repository's
settings because it would reset `main` to an upstream snapshot (see
[Disabled upstream workflows](#disabled-upstream-workflows)).

1. `fork-upstream-watch.yml` checks daily. When upstream has an unmerged
   release, the run fails (Issues are off, so the failure email is the
   notification) and its summary shows the command.
2. Locally, on a clean tree:

   ```sh
   node scripts/fork-sync-upstream.mjs start vX.Y.Z
   ```

   This creates `sync/vX.Y.Z` from `origin/main` and merges the upstream tag.
   It never pushes, and keeps upstream tags out of `refs/tags`.
3. On conflicts it stops with the merge in progress. Keep fork behaviour
   (fork-config, Windows update trust, ACP fixes), then `git commit`.
4. Run the gates, push the branch, open a pull request; `fork-ci.yml` must pass.

   ```sh
   bun install --frozen-lockfile
   bun test scripts/fork-invariants.test.mjs
   bun run typecheck && bun run typecheck:mobile && bun run build:web
   git push -u origin sync/vX.Y.Z
   ```

5. After merging, check that no new upstream workflow is active (see
   [Disabled upstream workflows](#disabled-upstream-workflows)).

Do not add database migrations in the fork: their sequential numbers would
collide with upstream's next ones.

### Disabled upstream workflows

GitHub can disable Actions for the whole fork ("Workflows on this fork have
been disabled … to reduce the amount of compute that is wasted") until a
maintainer re-enables them on the Actions page. While disabled, nothing runs,
including `fork-upstream-watch.yml`, so new upstream releases go unnoticed.
Inherited workflows are a likely trigger: their jobs are gated to
`tianma-if/edgeever`, but every push, pull request and release still starts a
run that is then skipped. GitHub does not publish its criteria, so this
reduces the risk without guaranteeing it.

These upstream workflows are therefore disabled in the repository (not in the
files, so upstream syncs do not conflict):

- `sync-edgeever-upstream.yml` (would reset `main` to an upstream snapshot)
- push or pull request: `acp-cleanup.yml`, `deploy-site.yml`,
  `deploy-tools.yml`, `docker-image.yml`, `extension-build.yml`,
  `ios-build.yml`, `mobile-build.yml`, `sync-docker-installer.yml`, `test.yml`
- release (fork releases trigger them too): `deploy-demo.yml`,
  `deploy-personal.yml`, `desktop-build.yml`, `docker-tcr-mirror.yml`,
  `extension-store.yml`

The `fork-*` workflows stay enabled, as do upstream workflows that only run
manually. A workflow file added by an upstream sync starts enabled, so list
the active ones after each sync:

```sh
gh api repos/lauchiwa/edgeever/actions/workflows --jq '.workflows[] | select(.state=="active") | .path'
```

Disable a new upstream entry with an automatic trigger with
`gh workflow disable <file> -R lauchiwa/edgeever`; undo it with
`gh workflow enable`.

## Releasing

1. Pick the tag on an up-to-date `main` and push it:

   ```sh
   git switch main && git pull --ff-only && git fetch --tags
   node scripts/fork-release-version.mjs next      # e.g. v1.119.0-rc.0
   git tag v1.119.0-rc.0 && git push origin v1.119.0-rc.0
   ```

2. `fork-release.yml` does the rest, with no manual step:
   - `windows`, `linux`, `macos` (arm64 and x64) and `android` run in parallel with a
     read-only token and no access to any signing key. Each checks the tag is on `main`, runs the
     release gates (including both pinned keys), applies the version, and
     builds and launches the app:
     - `windows` produces the installer, `rc.yml`, `latest-windows.json` and
       `SHA256SUMS-windows.txt`.
     - `linux` builds on Ubuntu 22.04 (glibc 2.35 baseline) and produces the
       AppImage, `rc-linux.yml` and `SHA256SUMS-linux.txt`. It then runs a
       real update: an older AppImage downloads the new one from a local feed
       serving only these assets, replaces itself and relaunches as the new
       version. The older AppImage is the previous published fork release
       with Linux assets, or, before one exists, this source built as
       `0.0.1-rc.0`.
     - `macos` builds the unsigned app for each architecture, plus its update
       predecessor (chosen the same way as for Linux).
     - `android` builds the arm64-v8a APK, signed only with the template's
       debug key.
   - `macos-sign` runs in the `fork-macos` Environment, installs nothing, and
     signs both apps (and a built predecessor) with the primary certificate,
     then packs each into a zip, a disk image, `rc-mac.yml` and
     `SHA256SUMS-macos.txt`.
   - `macos-verify` checks the signatures, launches each signed app, and runs
     a real update on each architecture: the older signed app downloads the
     new zip from a local feed, Squirrel.Mac checks it against the running
     app's requirement and replaces the bundle, which must then hold exactly
     the signed app.
   - `android-sign` runs in the `fork-android` Environment, installs nothing,
     signs the APK with the fork keystore, fails unless the only signer is the
     one in `FORK_ANDROID_SIGNER_SHA256`, and stages
     `EdgeEver-X.Y.Z-rc.N-android-arm64.apk` with `SHA256SUMS-android.txt`.
   - `draft` runs only once every platform passes and uploads all fifteen
     assets as a **Draft** pre-release, with a per-platform download table in
     the notes. A failure on any platform creates or
     changes no Draft.
   - `publish` signs `latest-windows.json`, uploads the signature, downloads
     all sixteen assets again, audits the Windows, Linux and macOS assets
     exactly as a client would, checks the APK against its checksum list and
     its signer with `apksigner` again, and publishes only if that passes.

   Clients never see Drafts, so a failure is safe to retry: fix the cause, then
   run the workflow manually with the same tag (Actions → Fork release →
   Run workflow on `main`).
3. Local fallback, for example if the Environment secrets are unavailable
   (PowerShell or Windows Terminal, not Git Bash; the passphrase is prompted):

   ```powershell
   $env:EDGE_EVER_WINDOWS_UPDATE_SIGNING_KEY = "$HOME\.config\edgeever-fork\windows-update-ed25519-primary.pem"
   node scripts/fork-sign-release.mjs v1.119.0-rc.0 --publish
   ```

The same tag also triggers `fork-docker-image.yml`, which builds the server
image (see below). The two workflows are independent: a failed image does not
hold back the desktop release, and can be rebuilt by running the workflow
manually with the same tag.

A tag with a wrong base does not need deleting; publish a correct, higher tag.
Never delete or re-sign a published release.

## Server image

`fork-docker-image.yml` runs on every `vX.Y.Z-rc.N` tag on `main`:

- `test` builds the image and runs it: health, the Web app, SQLite under
  `/data`, `features.encryptedNotes`, and a graceful shutdown.
- `publish` pushes `linux/amd64` and `linux/arm64` to
  `ghcr.io/lauchiwa/edgeever`, then pulls and runs the pushed image again.

Tags: `:vX.Y.Z-rc.N`, `:X.Y.Z-rc.N`, and a moving `:rc` that follows the
highest rc tag. `:latest` is never published, so a server still on upstream
defaults cannot pick up a fork image by accident, and vice versa.

A new GHCR package usually starts private; the `publish` summary warns when
anonymous pulls fail. Either make it public
(GitHub → Packages → edgeever → Package settings → Change visibility), or run
`docker login ghcr.io` on the server with a token that has `read:packages`.

### Switching a server to the fork image

The installer's daily `update.sh` keeps whatever image `~/edgeever/.env` names,
so the switch is two lines in that file. Take a cold backup first: a fork
image on an older upstream base would run against a database migrated by a
newer upstream image.

```sh
cd ~/edgeever
docker compose --env-file .env stop edgeever
docker run --rm -v edgeever_edgeever-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/edgeever-data-$(date +%Y%m%d%H%M).tgz -C /data .
# in .env:
#   EDGE_EVER_IMAGE='ghcr.io/lauchiwa/edgeever'
#   EDGE_EVER_VERSION='v1.119.0-rc.4'   # pin; or 'rc' to follow fork releases
docker compose --env-file .env pull && docker compose --env-file .env up -d
curl -fsS http://127.0.0.1:8787/api/v1/auth/session   # features.encryptedNotes: true
```

Check the volume name with `docker volume ls` first. Do not move to a fork
image whose `X.Y.Z` is below the upstream version the server runs now; sync
upstream first.

Rollback: stop the service, restore the old values of `EDGE_EVER_IMAGE` and
`EDGE_EVER_VERSION`, restore the `/data` backup into an empty volume, and
start again. Encrypted notes stay ciphertext under an upstream image: readable
only after switching back, and editing them there would overwrite them.

## Android

Every rc release carries `EdgeEver-X.Y.Z-rc.N-android-arm64.apk`, signed with
the fork keystore. It never updates itself: download and install each new
release by hand. The app shows the `version` from `apps/mobile/app.json` (the
upstream app version), which may differ from the release number; installing
over the same or a higher `versionCode` works, so later releases install over
earlier ones.

The keystore is read only by two jobs, both in the `fork-android`
Environment, installing nothing: `android-sign` in `fork-release.yml` on an rc
tag, and `sign` in `fork-android.yml` on a manual run. Anyone in control of
this GitHub account or of a release run can therefore sign an APK that
installs over the fork app, the same boundary as for the Windows and macOS
keys.

### Test builds between releases

`fork-android.yml` builds an APK from `main` for testing before the next tag.
It is not a release asset.

- Pull requests that touch the app run `build` only: type check, encrypted
  note tests, prebuild, a check that expo-updates is off, and the Gradle
  release build. No secret is available there.
- Actions → Fork Android test build → Run workflow (on `main`) also runs
  `sign`. It runs in the `fork-android` Environment, installs nothing, signs
  the APK with the fork keystore, and fails unless the only signer is the one
  in `FORK_ANDROID_SIGNER_SHA256`. Download `edgeever-fork-android-apk` from
  the run (kept 30 days); the summary shows its SHA-256.

One-time keystore setup, by the maintainer (PowerShell; the agent never reads
the keystore or its password):

1. Create the Environment: Settings → Environments → New environment
   `fork-android`. Limit deployments to the branch `main` and the tag
   pattern `v*-rc.*`, like `fork-release` and `fork-macos`; without the tag
   rule, `android-sign` cannot start and the release stays unpublished.
2. Create the key (`keytool` prompts for the password; PKCS12 uses it for the
   key too):

   ```powershell
   keytool -genkeypair -v -storetype PKCS12 -keystore "$HOME\.config\edgeever-fork\android-fork.p12" -alias edgeever-fork -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=EdgeEver fork"
   keytool -list -v -keystore "$HOME\.config\edgeever-fork\android-fork.p12" -alias edgeever-fork
   ```

3. Store it (stdin keeps the keystore out of the command line; the password
   is typed hidden). The variable is the `SHA256:` line printed above:

   ```powershell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("$HOME\.config\edgeever-fork\android-fork.p12")) | gh secret set FORK_ANDROID_KEYSTORE_BASE64 --env fork-android -R lauchiwa/edgeever
   gh secret set FORK_ANDROID_KEYSTORE_PASSWORD --env fork-android -R lauchiwa/edgeever
   gh variable set FORK_ANDROID_SIGNER_SHA256 -R lauchiwa/edgeever --body "<SHA256 fingerprint>"
   ```

4. Back up the `.p12` file and its password offline. Without them, a later
   build cannot install over the current one; the app then has to be
   uninstalled, which drops its local cache (data on the server is kept).

Installing: the package name matches upstream's but the signer differs, so
Android refuses to install over the upstream app. Uninstall it first (its
local cache and unsent offline edits are lost), install the fork APK, and log
in again. Later fork builds install over each other.

## Linux AppImage

- For x64 distributions with glibc 2.35 or later (such as Ubuntu 22.04+).
  AppImages need FUSE 2: install `libfuse2` on Ubuntu 22.04, `libfuse2t64` on
  Ubuntu 24.04.
- Download `EdgeEver-X.Y.Z-rc.N-linux-x64.AppImage` from Releases, optionally
  check it with `sha256sum --check SHA256SUMS-linux.txt`, `chmod +x` it and run
  it directly. **It updates itself only when the AppImage file is run
  directly**, not when extracted or integrated by a third-party tool.
- Updates download in the background and replace that AppImage file, so the
  file and its directory must be writable by the user.
- Upstream's Linux Preview (bare versions) does not update to a fork release;
  download the fork AppImage by hand.
- **Linux updates are not signed:** anyone who can change this fork's
  Releases (the GitHub account or a release run) can ship an update installed
  Linux clients accept. The Windows signing key is stored in GitHub as well,
  so for both platforms the boundary is this GitHub account.

## macOS

- Two downloads: `EdgeEver-X.Y.Z-rc.N-mac-arm64.dmg` (Apple silicon) and
  `-mac-x64.dmg` (Intel), for macOS 13 or later. Optionally check them with
  `shasum -a 256 -c SHA256SUMS-macos.txt` (other lines report missing files).
- **The app is not notarized, so Gatekeeper blocks its first launch.** Drag
  EdgeEver into Applications from the disk image, open it once, then allow it
  in System Settings → Privacy & Security → Open Anyway. Or remove the
  download flag in Terminal: `xattr -dr com.apple.quarantine /Applications/EdgeEver.app`.
- Updates download the full zip in the background (no blockmaps, so no
  differential downloads) and install when the app restarts. The app must stay
  in a folder the user can write to, such as `/Applications`.
- The fork keeps upstream's bundle id, so it replaces an upstream install and
  keeps its data, but the two never update each other: their designated
  requirements differ. Over an upstream install, macOS will likely ask once
  whether EdgeEver may use the "EdgeEver Safe Storage" keychain item (choose
  Always Allow); denying it signs the desktop app out.
- **macOS updates are trusted through the fork's certificate**, whose key is
  stored in GitHub like the Windows one: for every platform the boundary is
  this GitHub account.
- The WeChat share extension ships signed with the same certificate.

## Installed clients

- Builds made before the fork's update feed existed (bare versions such as
  `1.119.0`) cannot auto-update to `1.119.0-rc.0`, which ranks lower. Install
  the first fork release by hand; later fork releases then update in place.
- The installer keeps the app id and data directory, so installing a fork
  build over an upstream one keeps local data.
